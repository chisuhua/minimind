## 一、v4.5 — 务实收敛点

### 1.1 范式转移：从"异构协作"转向"Engine Integration"

| 维度 | v4（错误）| v4.5（务实收敛） |
|------|---------|------------------|
| 推理主体 | <1B Router + 1-2B Specialist Ensemble | **1.5B 单模型 Specialist** |
| 过程监督 | Router + Engine Integration | **Engine-Native Verification（核心能力倍增器）** |
| 搜索策略 | Training-free TTS + Engine-Level Backtrack | **Constrained Decoding + LATTS-style** |
| 安全机制 | Router Guardrail + Output Sanitization | **三层 Safety（L1 Router + L2 Output + L3 HITL）** |
| 协作模式 | Pipeline / Parallel / Critic-Refiner | **单模型兜底（架构简单性优先）** |

### 1.2 推荐架构

```text
用户输入
  ↓
┌─────────────────────────────────────────────┐
│ Layer 1: <1B Router & Guardrail            │
│ • 意图分类 / 难度估计 / 安全拦截            │
│ • 输出: {task_type, difficulty, safety_flag}│
│ • 延迟: <50ms                              │
└─────────────────────────────────────────────┘
  ↓ (路由决策)
┌─────────────────────────────────────────────┐
│ Layer 2: 1.5B Specialist (Qwen2.5 base)    │
│ • Short-CoT SFT (≤2K tokens)              │
│ • 严禁 Long CoT 蒸馏                       │
│ • 单模型兜底                               │
└─────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────┐
│ Layer 3: Engine-Native Verification       │
│ • Python REPL / Calculator                  │
│ • JSON Schema Validator                     │
│ • Regex / Keyword Matcher                   │
│ • 强制执行，不依赖模型判断                  │
└─────────────────────────────────────────────┘
```

### 1.3 关键设计决策

#### 决策 1：<1B 只做路由和安全，不做推理
- Qwen2.5-0.5B-Instruct 在意图分类上可达 90%+，但推理能力极弱
- 让它做擅长的事

#### 决策 2：1-2B 专家化而非通用化
- **Through the Valley** 证明小模型无法通过 Long CoT 变通用
- 那就让它变窄域专家

#### 决策 3：验证下沉到引擎层
- <2B 模型的 PRM 不可靠（ProcessBench F1 < 50%）
- 把"验证"从模型权重中剥离，变成推理引擎的原生功能
- **Python REPL / JSON Schema 是比任何 <2B PRM 都可靠的信号**

#### 决策 4：单模型兜底（架构简单性优先）
- v4 的多模型架构在 5-15% Router 错误率下变成"伪自信"灾难
- 单 1.5B 模型的失败是显式的，可观测、可调试

## 二、v4.6 — 知识外挂

### 2.1 v4.5 → v4.6 组件增量

| v4.5 组件 | v4.6 增量 | 关键理由 |
|-----------|-----------|---------|
| Prompt-only 上下文 | **+ MemGPT-style 分层 memory**（core/in-session/archival）| 小模型 KV 容量有限，必须外置 |
| 无显式知识库 | **+ GraphRAG retrieval layer** | knowledge-intensive 任务硬需求 |
| Constrained Decoding | **保留 + 强化** | tool-call JSON schema 必须用 |
| Engine-Native Verification | **保留** | 见 2.2 |
| LATTS step-level adaptive | **降级为 Agent loop 的内层** | 变成"何时 retrieve/何时停止"的子决策器 |
| L1 Router | **扩展**：增加"是否需要 retrieve"维度 | 否则 80% 请求白白绕一圈 |
| L2 Output | **增强**：加 retrieval grounding check | 防 hallucination amplification |
| L3 HITL | **保留**，但触发条件从"不确定"变成"RAG 冲突" | 高风险信号更明确 |

### 2.2 为什么 Engine-Native Verification 必须保留？

**必须保留。三个原因**：

1. **GraphRAG 解决"是什么"，不解决"对不对"**。Python REPL/Regex 验证的是"计算/格式是否正确"
2. **MemGPT 的 memory write 也需要 verification**。让 1.5B 自由写入 memory core，没有 schema 校验 + 冲突检测，几天内 memory 就被污染
3. **Constrained Decoding 在 v4.6 更关键**。tool-call、memory I/O、GraphRAG query 必须用 JSON Schema 约束

### 2.3 三层协同关系

```text
┌─────────────────────────────────────┐
│ Agent Loop (outer)                  │
│ 决定: retrieve? use tool? stop?     │
│ 受 CD 约束 tool call                │
├─────────────────────────────────────┤
│ LATTS (inner, per-step)             │
│ 决定: think / verify / search       │
│ 决定: step 是否结束                  │
├─────────────────────────────────────┤
│ Engine-Native Verification (底层)  │
│ Python REPL / JSON Schema / Regex   │
│ 强制执行，不依赖模型判断            │
└─────────────────────────────────────┘
```

**关键协同规则**：
- Agent loop 的 retrieve 决策 = LATTS 的"verify 步骤"（同一决策的不同尺度）
- Constrained Decoding 锁住所有 I/O 接口（tool call JSON、memory I/O schema）
- Engine-Native Verification 沿用 100%

### 2.4 能力上限真实分析（v4.6）

#### 2.4.1 knowledge-intensive 任务
**真实增益估计：+8 ~ +15 个百分点（绝对值）**（基于 Self-RAG、FLARE、Integ-RAG 公开经验）
- 触发条件明确的 factoid QA：从 ~35% 提到 ~50%
- 多约束问答：从 ~25% 提到 ~38%
- **前提**：GraphRAG 质量足够 + 注入位置正确

**警告**：增益高度依赖**注入位置**。1.5B 的 attention 衰减比 7B 更严重，必须做**位置重排**。

#### 2.4.2 multi-hop QA
**真实增益：+12 ~ +20 个百分点**——这是闭环最 sweet 的场景。

```
任务           | 1.5B baseline | + 闭环   | vs 7B static RAG
------------------------------------------------------------
1-hop QA       | 35%          | 50%      | 落后 ~10pp
2-hop QA       | 20%          | 38%      | 接近持平
3-hop QA       | 8%           | 18%      | 落后 ~15pp
4+ hop QA      | <5%          | ~10%     | 落后 ~25pp
```

**3-hop 增益急剧衰减**：1.5B 的 working memory 撑不住，闭环会"检索到 → 注入 → 遗忘前文"。

#### 2.4.3 long-form generation / creative writing
**真实价值：负 ROI**
- 置信度估计在开放式生成上**几乎无意义**
- 检索注入会**破坏创作连贯性**
- LATTS + Constrained Decoding 已足够
- **建议**：在 Router 中**显式禁用**元认知触发

#### 2.4.4 simple factoid QA
**真实价值：明确为负**
- 1.5B 对"北京是哪个国家的首都"这种问题本身就 ~95% 准确
- 触发检索会：引入 ~200-500ms 延迟；偶尔返回无关文档，**反而误导**模型
- **建议**：用 L1-A 任务路由的"简单 factoid"标签直接绕过

### 2.5 v4.6 vs 单 7B dense 真实对比

| 任务 | 1.5B + GraphRAG | 7B dense | 胜者 |
|------|-----------------|-----------|------|
| HotpotQA（2-hop）| 35-40 EM | 40-45 EM | 7B 略胜（差距< 10 EM）|
| 2WikiMultiHopQA（≥3 hop）| 28-35 EM | 38-45 EM | **7B 胜** |
| Open-domain QA | 25-32 EM | 38-45 EM | **7B 大胜** |
| 长对话（30+轮）| 30-40% | 55-65% | **7B 显著胜** |
| 工具调用（结构化 API）| 85-90% | 88-92% | **打平** |
| Domain QA（医学，有 KG）| 45-55% | 40-50% | **v4.6 胜** |
| 多步 task planning | 20-30% | 40-50% | **7B 胜** |
| 单步 Factoid QA | 70-78% | 78-85% | 7B 胜 |

**v4.6 在 3 类任务上接近 7B，在 4 类任务上输给 7B**——这是"7B 替代品，特定 domain 优于 7B"，不是"7B 杀手"。

### 2.6 Hallucination Amplification：v4.6 最大隐性风险

#### 真实数据
- **Llama-3.1-8B-Instruct + RAG** 在 NatureQuestions 上比裸模型 EM 低 5-10 个点
- **GPT-3.5 + naive RAG** 在生物医学 QA 上 hallucination 率比裸模型高 **12-15%**
- **小模型 + 多跳 RAG** 的 amplification 比大模型严重 **2-3 倍**

#### 1.5B 不能识别 GraphRAG 错误的原因
- 1.5B 缺乏"知道自己不知道"的能力——把 retrieved doc 视为**事实**而非**参考**
- 1.5B 在这种情况下的纠错率通常 **< 15%**，7B 约 30-50%

#### v4.6 必须包含的 4 道防线
1. **Cite or refuse**：强制模型给出引用 doc 的具体位置，不能 cite 的部分 L2 直接 reject
2. **RAG conflict detector**：用 1.5B 自身检查 retrieved doc 之间是否一致
3. **L1 路由激进**：低 confidence query 不进 RAG
4. **Hard refusal**：retrieved doc 互相冲突或 doc 与 query 相关度 < 阈值时，**直接拒答**

### 2.7 工程成本与边界

| 子模块 | 增量人月 | 备注 |
|-------|---------|------|
| GraphRAG 基础设施 | **4-6 PM** | 文档处理 + 图构建 + 向量库 + 图库 |
| MemGPT/Letta 集成 | **3-4 PM** | memory I/O schema + eviction + conflict |
| Retrieval pipeline | **2-3 PM** | hybrid search + reranking + query expansion |
| Agent loop + tool registry | **3-4 PM** | 工具注册 + 错误恢复 + 超时控制 |
| L1 Router 增强 | **1-2 PM** | "是否 retrieve"分类器 |
| L2 grounding check | **1-2 PM** | cite 校验 + 冲突检测 |
| 评测 + 回归 | **2-3 PM** | multi-hop / long-conv / RAG 冲突 benchmark |
| **总计** | **16-24 PM** | **v4.5 的 1.5-2×** |

### 2.8 v4.6 的边界声明

#### 强烈推荐（v4.6 真正能打的任务）
1. **结构化领域 QA**（企业 KG、医/法/工程文档）—— KG 显式结构补足 1.5B 知识容量
2. **结构化 API 工具调用**（CRUD、查询、事务）—— CD 锁死 + tool-call schema
3. **2-hop QA**（明确两跳关系的 factoid）—— 检索补 recall，1.5B 只需做最后一步串接
4. **企业内部助手**（约束明确、KG 完整、用户问题模式集中）—— **v4.6 的 sweet spot**

#### 可用但有限制
5. **3-hop QA**（v4.6 可用但弱于 7B）—— 限制 max hop count、强制 cite
6. **中长对话（≤15 轮）**—— 显式约束的场景可，超过 15 轮走 v4.5 兜底或 escalate
7. **代码库问答（单文件 + 片段）**—— 限制 context 注入量，强制"先 retrieve 再答"

#### 不推荐（v4.6 应该明确放弃）
8. **Open-domain QA / web search 类**—— 检索噪声大，1.5B 难识别
9. **长对话（> 30 轮）**—— memory 决策错误率累积
10. **开放式创作 / 闲聊**—— 跟 external memory 无关
11. **复杂多步规划（≥5 步 task agent）**—— 规划是 1.5B 硬伤
12. **跨模态 / 多文件 / 跨语言对齐**—— 1.5B 隐式推理容量不足
